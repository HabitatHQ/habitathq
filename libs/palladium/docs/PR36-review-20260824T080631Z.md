## Blocking — correctness/security (must fix before merge)

### 1. `crates/atrium/src/routes/changes.rs:151–158` — non-atomic ACL record + change insert

The TODO at lines 144–150 admits it: every `POST /v1/changes` first writes ACL rows into Atrium's `records` / `shares` / `grant_events` tables, *then* writes the change to the *separate* palladium_changes store. A retry/crash between the two leaves ACL metadata that outlives a missing change (or vice-versa). With multiple members, this means a granted grantee can drift: their next poll sees an `insert_record` for a row whose change they never received. Retry-safety today relies on `insert_record` being `INSERT OR IGNORE` and the POC posting one row per change — fine for the harness, not for the tenancy contract.

Either move ACL metadata into the same SQL store as the change log, or wrap both writes in a single SQLite transaction with durable WAL.

### 2. `crates/atrium/src/routes/changes.rs:112–128` — `change_root` / `change_visible` use a *global* `records` lookup

The `records` PK is `row_id` *only*, with no `workspace_id` qualifier. Atrium keys every ACL check on `row_id` globally. **First-write wins owner.** Workspace A's habit `H1` (uuid) can never be owned by Workspace B's member even if B's grant path wanted to assign them — the owner column is silently frozen at A's first POST. The opposite hazard is worse: if any user anywhere manages to seed the same `row_id` (deterministic UUIDv5 names or migration imports), `effective_root()` returns that other workspace's ACL.

Either add `UNIQUE(row_id, workspace_id)` (with a composite FK) and qualify every `records` / `shares` lookup, or scope `records` under the workspace scope. With D5 already committed to owner-scoped UUIDs, the only correctness path is the composite key plus a workspace-aware ACL resolver.

### 3. `crates/atrium/src/routes/changes.rs:74–109` — children can be inserted under any root, and `insert_record` of a child always claims the caller as the owner, even if the root's owner is someone else

A collaborator who happens to learn a `root_id` can insert child rows that Atrium records with `owner_user_id = caller`. Subsequent `can_write` / `can_read` checks on the root still hold (the check goes through `effective_root`), so the leak is audit-only today — but `records.owner_user_id` will be wrong on every child row inserted by a non-owner grantee, breaking any future audit/owner-based queries (D5), and it implicitly widens the surface for future bugs in any code that reads `owner_user_id` without going through `effective_root`.

Set the child's `owner_user_id` to the *root's* owner, or store the child without `owner_user_id` (it carries no authority anyway).

### 4. `crates/atrium/src/routes/changes.rs:227–235` — `grant_events` `mark_delivered` runs unconditionally

Once a grant event is returned in a response, it's marked delivered *even if the client never receives it* (no client ack on the wire). On a dropped TCP the grantee permanently loses the purge/backfill (F9 in the doc's own follow-ups), and a revoked client permanently loses its purge. There's no `id` returned either — the client can't detect loss.

The plan notes "at-most-once is acceptable for the POC"; this is *only* OK if the comment stays — but the existing harness passes today because every test waits long enough. Tag the route with a `#[cfg(feature = "production")]` disabled gate, or fold it into the durable-event-ack TODO. As written, the docstring acknowledges the failure mode but the implementation looks finished — readers will assume it's correct.

### 6. `libs/palladium/core/src/sync.ts:265–291` `wireOpToEngine` / `engineOpToWire` — `insert` wire op trusts `data.id` over `row_id`

I confirmed empirically: an insert op with `row_id: "authorized-row"` and `data: { id: "different-row", … }` materializes a row whose at-rest `id` column is `"different-row"` and whose `_sync_row_meta` is keyed on the *engine insert path* (which spreads `data` over the row id and calls `applyOp`). The at-rest `id` and the row the engine stamps are therefore decoupled from the value Atrium authorized on `row_id`.

Concretely: a client can submit an insert whose `data.id` differs from the authorized `row_id`, and the server's ACL has no way to detect it — the row is materialized under a peer-chosen `id`. Either `wireOpToEngine` should ignore `data.id` and force `id: op.row_id`, or the wire format must be normalized at the boundary so server-side ACL keys on a single, authoritative identifier. (See the burrow POC where `AtriumApi.putBlob` and `engine.insert("note_images", { id: newId(), … })` flow through this exact path.)

Repro harness: see "Repro scripts" at the bottom.

## High — design-level risks worth raising now

### 7. `crates/palladium-postgres/src/store.rs:118–123` — `SET search_path TO {schema}` on every connection from the pool is not done

The migration creates the schema and runs `MIGRATE` against the pool, but every `sqlx::query` runs in the *default* `search_path` (so `palladium_changes` either doesn't resolve or, worse, another `palladium_changes` from a co-resident schema is hit). One `CREATE SCHEMA` is fine for a single-tenant Postgres, but with `PostgresIsolation::Schema` the route handlers do not run `SET search_path` per request; the runtime table name doesn't include the schema prefix.

Add `SET search_path` on each acquired connection (e.g. via `PoolOptions::after_connect`) or qualify every DML with `{schema}.palladium_changes` after validating `schema`.

### 8. `crates/palladium-sqlite/src/store.rs:18–29` — `CREATE TABLE IF NOT EXISTS` does not add `scope` to pre-existing tables

Same TODO comment as the Postgres store: an in-place upgrade on a non-fresh database will silently keep the old, scope-less rows, and the new `idx_changes_scope_hlc` index creation will fail (`column scope does not exist`). Palladium is pre-release, so the deferred migration is acceptable *iff* it's tracked in `docs/plans/follow-ups.md`. It is (F1), but I don't see a "mirror it in palladium-postgres" entry — the comment says "mirror it … when added," which is the wrong way around; add it to the follow-ups file now so the Postgres migration doesn't get forgotten when F1 ships.

### 10. `libs/palladium/core/src/sync.ts:560–574` — poll cursor advances per-change and is non-monotonic

`this.#cursor = hlcToAfterCursor(change.hlc);` is unconditional. Atrium's grant-backfill serves older-HLC changes *after* the grantee's current cursor; the client accepts and stores them, then overwrites `#cursor` with the backfill's older HLC. The next poll refetches everything newer than the backfill — wasteful but correct (idempotent apply saves you from divergence). Empirically confirmed via a targeted `vitest` repro (`expected 1700000000500 to be 1699000000000`).

The doc lists this as a "one-line monotonic-max guard" follow-up — fine, but the cursor is also persisted via `setSyncState(STATE_CURSOR, …)` *outside* a transaction, so even a happy-path crash window can leave the persisted cursor behind the in-memory one. Either compose the cursor advance as `monotonicMax(this.#cursor, change.hlc)` before persisting, or batch the persistence into the apply transaction. The bug self-heals (idempotent re-apply), but the bug exists.

### 11. `libs/palladium/core/src/engine.ts:586–602` `applyRemoteUpdate` — update on absent row stamps the metadata for a row that never existed

Acknowledged in `follow-ups.md` lines 78–85: when a remote update arrives before the row's insert, the shadow-table entry is written for a missing row, then the later insert overwrites both. The "winning" row keeps the new HLC on columns it *should* have lost, and the losing columns (which never existed) keep metadata that should never have been stamped.

The TODO lists the fix as "buffer updates for absent rows." With ordering hazards common in a multi-device sync (the POC tests show `alice1` and `alice2` both inserting before either has the other's row), this isn't a corner case — it's the everyday path. Buffer or persist.

I confirmed empirically: a stale replay of an older-HLC update arriving *after* a higher-HLC tombstone does NOT resurrect it — that's the test in `lww.test.ts:99` and it passes green. But the in-the-wild sequencing hazard (older update replayed against a never-inserted row) remains.

### 12. `libs/palladium/core/src/sync.ts:182–187` (`applyPurges` in `example-burrow/src/atrium.ts`) — the purge path emits a fresh-HLC delete via `applyRemote`

`engine.nextSendHlc()` mints a fresh HLC for the *local delete* — i.e., the device claims authorship of a delete it didn't author. Because `applyRemote` is idempotent on the tombstone and the data is being *removed*, the convergent state is correct, but the HLC is now in the change log under *this device's node id*. The server will broadcast that "this device issued the delete" to other members on their next poll, which:

- conflicts with the actual revoke event (different node ids for the same effect — fine because the LWW reconciles, but noisy).
- means the revoke event's own HLC gets "lost" in the canonical log (the local-delete HLC always wins because it's strictly greater than any remote HLC). The tombstone persistence is correct, but the *attribution* is wrong.

Either run the purge through the existing remote-delete HLC (fetch it from the revoke event in `get_changes` and use it) or accept the wrong attribution and document it. Today, no doc.

### 14. `example-burrow/src/sections/NotesSection.vue:84–126` — `loadThumb` calls `URL.revokeObjectURL` only on unmount, never on `thumbs.value` updates

After a revoke-purge wipes the row out of `note_images`, the corresponding object URL is still pinned in `thumbs.value` until the section unmounts. The watcher re-runs only when a row is added (or the image map grows), so a revoked thumbnail leaks until workspace/user switch.

Pair `loadThumb` with a watcher that revokes URLs whose `blob_id` no longer appears in `images`, or track `thumbs` as a `computed` of `images` + cache and release on each purge.

## Medium — correctness/clarity, defer-with-test improvements

### 15. `example-burrow/src/sections/NotesSection.vue:70–87` `attachImage` — `engine.insert` is called *after* `api.putBlob`

If the sync POST fails, the engine will retry the insert on the next start (durable outbox), but the blob will already be at Atrium under that `blob_id` with no referencing `note_images` row. A retry that ultimately succeeds leaves two `note_images` rows pointing at one blob (the second insert's HLC > first's, so the first is LWW-deleted — but the blob stays). Acceptable for POC; document or guard.

### 16. `crates/atrium/src/main.rs` — the `--insecure-allow-remote` guard was tightened in round 4 to check the *bound* `local_addr()`

Good (prevents a hostname resolving to a non-loopback IP from bypassing the check). The PR diff itself shows the second check; together with the textual check this is robust. One nit: the warning message in the original branch used `host = %cli.host` (named key), the replacement uses `%bound` — cosmetic, but the warning message text should mention `--insecure-allow-remote` as the override that was actually passed, otherwise operators can't audit logs for which flag bypassed the check.

### 17. `crates/atrium/src/db.rs:183–189` `upsert_user` is called per-write on the happy path

This is fine for SQLite WAL, but the `INSERT OR IGNORE` on every insert puts one statement in front of every ACL record. With grant-heavy workloads this is hundreds of redundant `app_users` upserts per poll. Pre-create or batch.

### 18. `libs/palladium/core/src/sync.ts:267–291` `wireOpToEngine` casts `op` to `keyof S & string` without runtime validation

If a malicious / buggy server sends an unknown `table`, the engine will happily materialize it as if it were a schema table (the engine applies by name, not by membership). Add a schema check before the cast (the `assertSqlIdentifier` exists, but no schema check). Atrium validates `role_of(table)` on `POST`; the client doesn't.

## Repro scripts

I ran two ad-hoc vitest cases in a temporary test file inside `.worktrees/pr-36/libs/palladium/core/src/__tests__/`. Both were deleted after confirming the behaviour; if the next agent wants to add them as regression tests, here are the shapes:

### `pr36-row-id-repro.test.ts` (proves #6)

```ts
import { describe, expect, it } from "vitest";
import { NodeSqliteAdapter } from "@palladium/sqlite-node";
import { PalladiumEngine } from "../engine.js";
import { SyncTransport, type WireChange } from "../sync.js";

type Schema = { notes: { id: string; title: string } };

async function makeEngine() {
  const engine = new PalladiumEngine<Schema>(
    new NodeSqliteAdapter({ vfs: { type: "memory" } }),
    { nodeId: "00000000-0000-0000-0000-000000000002" },
  );
  await engine.init({
    version: 1,
    schema: "CREATE TABLE notes (id TEXT PRIMARY KEY, title TEXT NOT NULL);",
  });
  return engine;
}

describe("PR36 row_id/data.id mismatch", () => {
  it("insert op: row_id is the authorized identity; data.id is at-rest", async () => {
    const engine = await makeEngine();
    const change: WireChange = {
      id: "00000000-0000-0000-0000-000000000010",
      hlc: { wallMs: 1_700_000_000_000, counter: 0, nodeId: "00000000-0000-0000-0000-000000000001" },
      ops: [
        {
          op: "insert",
          table: "notes",
          row_id: "authorized-row",
          data: { id: "different-row", title: "payload" },
        },
      ],
    };
    const transport = new SyncTransport(engine, {
      serverUrl: "http://example.invalid",
      fetch: async () =>
        new Response(JSON.stringify([change]), {
          status: 200,
          headers: { "content-type": "application/json" },
        }),
    });
    await transport.poll();
    const rows = await engine.adapter.exec<{ id: string; title: string }>(
      "SELECT id, title FROM notes",
      [],
    );
    // Insight: row_id drives the row identity, but `data` keeps the at-rest `id`
    // value as supplied by the peer. Atrium's ACL keys on row_id, so a mismatch
    // silently lets peers materialize records whose `id` column disagrees with
    // the server-authorized row_id — a class of ACL/identity drift.
    expect(rows).toEqual([{ id: "different-row", title: "payload" }]);
    await transport.stop();
  });
});
```

Result against `fd9285e`: PASSES (with the assertion as written — i.e., the bug exists and is observable).

### `pr36-cursor-monotonic.test.ts` (proves #10)

Drive `SyncTransport.poll()` with two changes where the second one has a strictly *smaller* HLC than the first (i.e., the grant-backfill scenario). After `poll()`, the persisted `_sync_state.cursor` was the *older* HLC, not the newer — so the next poll would re-fetch the newer work. Expected: `expect(parsed?.wallMs).toBe(1_700_000_000_500)`. Actual: `1699000000000`. Test fails; the bug exists.

(Test was deleted from `.worktrees/pr-36` after running — agent can recreate from the description above.)

Local insert → remote tombstone → older remote update: tombstone survives, no resurrection. Confirms the docs at `lww.test.ts:99` are accurate; the unreviewed corner is the absent-row case, which is what's listed as TODO in `follow-ups.md`.
