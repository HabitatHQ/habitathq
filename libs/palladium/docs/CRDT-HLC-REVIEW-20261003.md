# Palladium CRDT/HLC checklist review

**Baseline:** `bb05191ff185be7ca9868d5ac8acafc37b6d058a`. The two reproduced runtime defects below were remediated in the same-day lifecycle and clock-recovery change. User selected permanent row-ID retirement and explicit re-authoring of confirmed clock rejections, and authorized pre-alpha breaking changes. Other design recommendations are not implemented features or additional approved scope.

Reusable entry point: [Local-first sync design checklist](./SYNC-DESIGN-CHECKLIST.md). Current contract: [Sync Protocol v1](./SYNC-PROTOCOL-v1.md). This assessment does not establish full production readiness.

## Original questions

1. What constitutes object identity and replica identity?
2. What exactly happens for every kind of concurrent mutation?
3. Which CRDT implements each field/relationship, and why?
4. Where do we represent causality that HLC cannot represent?
5. What happens if a device clock is wrong by ±10 years?
6. Can every mutation be safely delivered zero, one, or many times and in arbitrary order?
7. What happens when a six-month-offline device returns?
8. How do deletes avoid resurrection?
9. Precisely when is it safe to GC operations/tombstones?
10. What happens if the app/server crashes after every individual persistent write?
11. How do old and new client versions interact?
12. Given a mysteriously wrong record, can we explain exactly how it reached that state?

## Source-backed answers after remediation

| #   | Answer                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Rows use UUIDv7; Changes and replica nodes use UUIDv4. Replica identity is not authorization; Atrium binds nodes to workspace members. Copying a database copies replica identity, HLC, and pending work. See [identity contract](./SYNC-PROTOCOL-v1.md#1-identity-changes-and-local-schema-identity).                                                                                                                                                                                        |
| 2   | Local transactions normalize to one final operation per row. Independent remote columns merge; competing scalar assignments use strict HLC LWW. A replicated delete permanently retires its row ID, independent of arrival order. See [engine](../core/src/engine.ts) and [lifecycle regressions](../core/src/__tests__/lww.test.ts).                                                                                                                                                         |
| 3   | **LWW registers are CRDTs.** They preserve a winner, not concurrent user intent. No general set/counter/sequence/relationship CRDT suite is supplied; domain constraints remain separate. See [engine](../core/src/engine.ts) and [operations](../crates/palladium-core/src/op.rs).                                                                                                                                                                                                           |
| 4   | HLC and per-column winning versions are stored; no vector/dot causal context detects concurrency. Server append positions order history paging, not causality. See [HLC](../core/src/hlc.ts) and [wire contract](./SYNC-PROTOCOL-v1.md#2-http-wire-contract).                                                                                                                                                                                                                                 |
| 5   | Authenticated history is structurally validated independently of receiver wall time. Authoring uses persisted server-calibrated time plus monotonic elapsed time; fresh uploads retain a server-relative five-minute bound. Explicit recovery reauthors only confirmed rejections; accepted/unrelated future floors cannot be lowered. See [clock contract](./SYNC-PROTOCOL-v1.md#21-authenticated-server-clock) and [recovery](./SYNC-PROTOCOL-v1.md#3-transactional-downlink-and-recovery). |
| 6   | Scoped content-checked idempotency preserves retries after lost acknowledgements. Accepted identical retries precede current-time checks; Atrium accepts valid reordered new node uploads. The reproduced lifecycle schedule converges in all six tested permutations. Zero delivery cannot ensure progress; this is not proof for arbitrary schemas/constraints. See [upload](./SYNC-PROTOCOL-v1.md#22-upload) and [simulation](../core/src/__tests__/sync-replica-simulation.test.ts).      |
| 7   | There is no established six-month retention/reset contract. Cursor paging and authorization/backfill require retained server history. See [download](./SYNC-PROTOCOL-v1.md#23-download) and [Atrium routes](../crates/atrium/src/routes/changes.rs).                                                                                                                                                                                                                                          |
| 8   | Terminal row tombstones suppress all later/same-ID inserts and edits, including higher HLCs; local reuse is rejected. Restore with a fresh UUID and deliberately update references. ACL purge remains per-view removal, so authorized regrant can replay history. See [engine](../core/src/engine.ts) and [regressions](../core/src/__tests__/lww.test.ts).                                                                                                                                   |
| 9   | No safe-GC horizon is established for append history, applied IDs, tombstones, or buffered updates. Exclude stale replicas/replay through a defined retirement or snapshot/reset contract before pruning. See [engine metadata](../core/src/engine.ts) and [history store](../crates/palladium-core/src/store.rs).                                                                                                                                                                            |
| 10  | Local rows, metadata, HLC, and registered outbox checkpoints commit atomically. Remote pages commit Changes individually, then purges/events/checkpoint together. Failed transactions also restore the in-memory clock. Process-crash tests are bounded; they do not establish every-write/power-loss/blob atomicity. See [transaction contract](./SYNC-PROTOCOL-v1.md#3-transactional-downlink-and-recovery) and [validation matrix](./TESTING-SYNC.md).                                     |
| 11  | Local schema identity and old-outbox quarantine are implemented, not server capability/schema negotiation. Upgrade all replicas and servers together for this breaking cutover; old servers without the clock endpoint cannot receive new-client uploads. See [identity/version contract](./SYNC-PROTOCOL-v1.md#1-identity-changes-and-local-schema-identity).                                                                                                                                |
| 12  | Payloads, append history, winning HLCs, applied IDs, and quarantine provide partial evidence. Clock recovery additionally preserves immutable originals and replacement mappings. There is still no complete overwritten-value/causal-parent/conflict-decision history or operator-facing winner explanation. See [quarantine/recovery](./SYNC-PROTOCOL-v1.md#3-transactional-downlink-and-recovery).                                                                                         |

## Data type → CRDT → causal metadata → conflict UX → GC rule

Recommendations below are domain choices, not implementation promises.

| Data type                  | CRDT                                                           | Causal metadata                                         | Conflict UX                                         | GC rule                                              |
| -------------------------- | -------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------- | ---------------------------------------------------- |
| Scalar (implemented)       | Per-column LWW register                                        | Winning HLC; no causal context                          | Silent winner                                       | Retain versions while stale replay is possible       |
| Intent-sensitive scalar    | **Recommendation:** multi-value register                       | Dot/context or durable ancestry                         | Show concurrent alternatives; explicit resolution   | Acknowledged resolution or replica-retiring snapshot |
| Set membership/labels      | **Recommendation:** OR-Set                                     | Unique add tags and remove context                      | Union; domain-specific remove/add feedback          | Retire replicas holding removed adds before tag GC   |
| Independent increments     | **Recommendation:** PN-counter/escrow                          | Per-replica components; bounded rights if needed        | Merge totals, not assignments                       | Proven replica retirement and stable compaction      |
| Ordered collection         | **Recommendation:** sequence CRDT when concurrency requires it | Stable element IDs, positions, causal context           | Deterministic order; expose incompatible intent     | Acknowledged horizon/snapshot before element GC      |
| Parent-child ownership     | Ordinary rows/foreign keys; choose domain policy first         | No relation-specific causal context                     | Field merge may violate domain invariants           | Defined referential and replica-retention policy     |
| Row deletion (implemented) | Permanent remove-wins retirement                               | Terminal tombstone; max delete HLC retained as evidence | Restore through a new UUID, never an implicit edit  | No established safe tombstone GC bound               |
| ACL visibility purge       | Not replicated deletion/CRDT                                   | Workspace/node event and backfill cursors               | Hide local view; authorized regrant replays history | Client purge does not authorize server history GC    |

HLC is a conflict version, not a history cursor, vector clock, or audit log. An append position prevents missing late-arriving old-HLC Changes, but does not detect concurrency. At-least-once retries require identity/payload idempotency; they do not guarantee delivery.

## Follow-up runtime findings

These are **historical counterexamples at the baseline**, not descriptions of the corrected engine. Inspect original code with `git show bb05191:libs/palladium/core/src/engine.ts` or the corresponding `hlc.ts` path.

- **Delete/update divergence:** identical `insert@1000`, `delete@2000`, `update@3000` left an absent row/tombstone/buffer for insert→delete→update, but retained `{title: "newer", body: "retained"}` for insert→update→delete. Complete replay preserved each outcome. Baseline locations: `engine.ts:1094–1117` buffered a missing-row update; `1120–1132` rejected deletion older than a data-field version. **Fixed:** terminal remove-wins retirement, pending-update cleanup, local ID-reuse rejection, fresh-ID restore, and delivery/restart regressions.
- **Slow receiver clock:** baseline `hlc.ts:31–49` rejected normal history against a ten-year-slow receiver. Correcting wall time alone did not lower a persisted future floor (`68–126`); Atrium also rejected reordered new node uploads (`atrium/db.rs:1349–1398`). **Fixed:** structural/admission separation, authoritative clock calibration, duplicate-first admission, and explicit outcome-confirmed recovery without rewriting accepted or uncertain Changes.
- Recovery integration additionally covers overlapping original/replacement HLCs: snapshot each register once and remap by immutable key, preventing cascading restamps. Original archive, metadata remap, and replacement outbox rows share one transaction. Malformed receipts, outbox races, and archival failures preserve pending work.

## Verification and limits

- `just build-palladium-ts lint-palladium-ts typecheck-palladium-ts test-ts` passed across maintained TypeScript packages; core passed **352 tests**. E2E typecheck and the full live-server suite passed **54 tests**.
- Affected Rust tests passed **169 tests**. The PostgreSQL `integration-tests` feature gate passed **5 tests**, including two live-database regressions against an isolated instance. Strict all-features/all-targets Clippy passed for core, SQLite, PostgreSQL, Axum, and Atrium.
- Standalone built-code smoke with actual SQLite clients/Rust HTTP exercised six lifecycle permutations plus duplicates, rejected retired-ID reuse, fresh-ID restoration, file reopen, immutable original→replacement evidence, drained recovery outbox, and a ten-year-slow receiver receiving and authoring an accepted edit. HTTP smoke verified `clock_skew`, content conflicts, and one append for identical retries. Integrated primary core build/lint/typecheck/unit verification and the same client smoke also passed.
- Dependency architecture passed in the isolated worktree; scoped Semgrep passed in the primary checkout. Primary `pnpm lint:deps` is blocked by an unrelated generated circular import under `apps/habitat/playwright-report/trace/assets/`; those existing files were preserved. The earlier ephemeral-port collision was resolved before the final complete E2E run.

These checks do **not** prove unbounded convergence, six-month/offline GC safety, causal intent preservation, mixed-version negotiation, every-write/power-loss safety, replica-clone recovery, cross-tab writer ownership, or blob/SQLite atomicity. Those remain explicit design/operational contracts, not hidden guarantees. See [TESTING-SYNC.md](./TESTING-SYNC.md).
